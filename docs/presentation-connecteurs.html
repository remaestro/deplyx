Deplyx — Connecteurs v2

🔧 Le problème

Chaque constructeur réseau a ses propres commandes, formats et API. Sans couche d'abstraction, l'intégration est un cauchemar.

🏢

Multi-constructeurs

Cisco, Juniper, Fortinet, Palo Alto, Huawei…
Chacun avec son OS, ses commandes, son parsing

📋

Duplication de code

Un connecteur par constructeur → 20 fichiers qui font la même chose avec des syntaxes différentes

🔌

Transports multiples

SSH (Netmiko), API REST, SNMP… chaque constructeur a ses préférences

🧠

Parsing hétérogène

TextFSM, regex, XML, JSON… et quand rien ne marche, il faut interpréter du texte brut

Deplyx — Connecteurs v2

✅ La solution — Architecture V2

Une seule classe, des profils YAML, un LLM pour la génération.

📄 Profils YAML

Chaque constructeur = un fichier YAML de ~30 lignes.
Pas de code Python à écrire.

# profiles/cisco-ios.yml
name: cisco-ios
vendor: cisco
transports:
- type: ssh
device_type: cisco_ios
commands:
show_version: "show version"
show_interfaces: "show interfaces"

🏗️ Architecture

Du YAML au graphe Neo4j — le flux complet

📄 Profil YAML → 🔍 UnifiedConnector → 🔌 SSH / API → 📊 Neo4j
Fingerprint → Profile matching → Collecte commandes → Parsing TextFSM/LLM → Normalisation → Push Neo4j

# Exemple de profil généré par le LLM pour Huawei VRP

name: huawei-vrp
vendor: huawei
os: vrp
match_banner:
- Huawei
- VRP
transports:
- type: ssh
device_type: huawei_vrpv8
commands:
show_version: "display version"
show_interfaces: "display interface"
show_ip_route: "display ip routing-table"
show_vlan: "display vlan"
show_bgp: "display bgp peer"
show_arp: "display arp"

✨ Résultat

Le LLM adapte les commandes au constructeur :
display version au lieu de show version
display interface au lieu de show interfaces
